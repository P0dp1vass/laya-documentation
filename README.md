# Laya: документация и production-примеры

Представим, что в поддержку приходит письмо: «За март списали оплату дважды. Прошу вернуть повторное списание». Человеку обычно понятно, что речь идёт о деньгах, а не о технической неисправности. Программе же нужно объяснить, на какой вопрос мы хотим получить ответ: определить отдел, заметить просьбу о возврате или оценить срочность обращения. Именно для таких задач и предназначена Laya.

При этом Laya работает не так, как привычный чат-бот. Она не пишет письмо клиенту и не придумывает объяснение своего решения. Вместо этого мы передаём ей текст, задаём вопрос и описываем допустимые ответы. Модель оценивает эти варианты, а программа получает метку, число или оценку вероятности. Такой ответ удобно использовать в коде, однако ограниченный набор вариантов ещё не означает, что выбор обязательно окажется правильным.

Этот репозиторий помогает разобраться в **Laya 0.4.21** и попробовать её в шести прикладных задачах. Здесь есть два подробных руководства, исходный код примеров и небольшие учебные данные. Под словом *production* мы будем понимать работу программы с реальными запросами пользователей, где уже важны ошибки, доступ к данным и последствия принятых решений. Поэтому примеры не только вызывают модель, но и показывают, в какой момент разумнее остановиться и передать решение человеку.

**Это не официальный репозиторий Laya.** Сама модель и её библиотека разрабатываются в [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya). Здесь мы разбираем их устройство и добавляем свой код для практического применения. В руководствах это разделение сохраняется: возможности официальной библиотеки и поведение наших примеров не выдаются за одно и то же.

> Веса модели в репозиторий не включены. Веса — это большие файлы с числовыми параметрами, которые модель получила во время обучения. При первом настоящем предсказании они могут скачиваться с Hugging Face, где опубликованы модели. На машине подготовки эти файлы не загружались и модели не запускались. Ниже приведены инструкции для вашей проверки, а не обещание уже измеренной точности или скорости на любом оборудовании.

## С чего начать

Если вы только знакомитесь с Laya, не нужно сразу читать все формулы или разбираться в Docker. Сначала полезно понять, какой ответ вы хотите получить от модели и чем он отличается от действия вашей программы. Например, «клиент просит вернуть деньги» — это результат анализа текста, а «клиенту положен возврат» — уже отдельная бизнес-проверка. В этом проекте модель не получает права самостоятельно переводить деньги или удалять сообщения.

Дальше можно выбрать удобный порядок чтения. Первое руководство отвечает на вопрос «как это устроено», а второе — «как этим пользоваться и что проверять перед реальной работой».

|---|---|
| Как работают модель, её архитектура, математика и три варианта весов | [01_LAYA_GUIDE.md](01_LAYA_GUIDE.md) |
| Что показывают все 41 официальный учебный пример | [Карта примеров в общем руководстве](01_LAYA_GUIDE.md#15-карта-официальных-примеров-0141) |
| Как установить зависимости, запустить примеры, API и Docker | [02_PRODUCTION.md](02_PRODUCTION.md) |
| Где задаются вопросы модели и описываются варианты ответа | [production/schemas.py](production/schemas.py) |

| Какие версии моделей выбраны и какие проверки действительно проводились | [models.lock.json](models.lock.json), [delivery_manifest.json](delivery_manifest.json) |

Для первого знакомства достаточно пройти установку, открыть справку `--help` и запустить один пример на своей машине. Затем будет проще читать подробные объяснения: названия полей и параметров уже будут связаны с тем, что вы увидели в выводе программы. Если же сейчас вы хотите только изучить документацию, устанавливать библиотеку и скачивать веса вообще не обязательно.

## 1. Скачать репозиторий

Репозиторий — это папка проекта вместе с историей её изменений. Команда `git clone` скачивает эту папку с GitHub, а `cd` переводит терминал внутрь неё:

```bash
git clone https://github.com/P0dp1vass/laya-documentation.git
cd laya-documentation
```

Все следующие команды предполагают, что терминал находится **в корне проекта**, то есть рядом с файлами `README.md` и `requirements.txt`. Это важно: когда программа открывает `data/tickets.jsonl`, она ищет файл относительно текущей папки.

Если вы уже скачали проект и ваша папка называется `laya-production-guide`, менять её название не нужно. Достаточно перейти в неё. Само имя папки не влияет на работу модели.

## 2. Установить окружение

Коду Laya нужны дополнительные библиотеки. Например, PyTorch выполняет вычисления нейросети, а Transformers помогает работать с её архитектурой и файлами. Если устанавливать всё прямо в системный Python, зависимости разных проектов могут начать мешать друг другу. Поэтому здесь используется отдельное виртуальное окружение `.venv` — собственный набор библиотек для этой папки.

В качестве исходного варианта выбрана версия **Python 3.12**. Команда ниже создаёт окружение, а следующая обновляет в нём `pip`, программу для установки Python-пакетов:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
```

Мы обращаемся к `.venv/bin/python` напрямую. Поэтому отдельно активировать окружение не требуется, и эти команды одинаково подходят для Bash, Zsh и Fish на Linux/macOS. Если терминал сообщает, что `python3.12` не найден, сначала нужно установить эту версию Python. Это ещё не ошибка Laya: до её установки мы пока не дошли.

Теперь нужно выбрать, где будут выполняться вычисления. **CPU** — обычный процессор компьютера. **GPU** — графический процессор, который способен обрабатывать много похожих операций одновременно. Для знакомства можно использовать CPU; подходящая GPU бывает полезна для большей нагрузки и длинных документов. Однако наличие видеокарты само по себе не означает, что установленная библиотека умеет с ней работать.

Выберите **одну** из двух команд установки PyTorch.

**CPU, без NVIDIA:**

```bash
.venv/bin/python -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cpu
```

**NVIDIA GPU, CUDA 12.8 wheel:**

```bash
.venv/bin/python -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cu128
```

Здесь `--index-url` указывает, откуда взять сборку PyTorch. Во втором случае это сборка для CUDA — программной среды вычислений на NVIDIA GPU. Слово *wheel* означает готовый установочный пакет Python, а не отдельную разновидность модели. Такой пакет всё равно требует совместимого драйвера видеокарты.

Для Apple MPS, Intel XPU или другой версии CUDA путь установки может отличаться. В таком случае нужно свериться с [инструкцией PyTorch](https://pytorch.org/get-started/locally/) и при необходимости изменить ограничение версии torch в reference-файле. Эти два варианта не обещают одинаковую совместимость со всем существующим оборудованием.

После PyTorch можно установить остальные зависимости проекта:

```bash
.venv/bin/python -m pip install -r requirements.txt -c constraints-reference.txt
.venv/bin/python -c "import importlib.metadata as m; print(m.version('laya'))"
```

Первая команда читает список пакетов из `requirements.txt`, а файл `constraints-reference.txt` задаёт ограничения на версии основных ML-библиотек. Вторая команда выводит установленную версию Laya, не выполняя предсказание. Для этого комплекта ожидается `0.4.21`.

Ограничения версий нужны не ради формальности: одна и та же конфигурация модели может по-разному читаться разными версиями библиотек. При этом наш файл не фиксирует каждую косвенную зависимость, то есть не является полным *lock-файлом*. Подробнее это разобрано в [production-руководстве](02_PRODUCTION.md#2-окружение-и-воспроизводимость). Системный Python 3.14 не стоит считать проверенной заменой выбранному окружению Python 3.12: установка старых зависимостей под ним уже сталкивалась с несовместимостью.

**Если вы работаете в Windows**, создайте окружение командой `py -3.12 -m venv .venv`. Затем вместо `.venv/bin/python` используйте `.\.venv\Scripts\python.exe`. Имена Python-модулей сохраняются, а команды запуска Docker имеют тот же смысл. Различия оболочек для переменных окружения отдельно объясняются в подробном руководстве.

## 3. Первый пример

Начнём с вопроса о возврате. Прежде чем загружать модель, можно посмотреть, какие параметры принимает программа:

```bash
.venv/bin/python -m examples.01_refund --help
```

`--help` означает «показать справку». В этом режиме веса не скачиваются и предсказание не выполняется. Поэтому с него удобно начинать, если вы пока хотите убедиться, что запускаете нужный файл из нужной папки.

Следующая команда уже передаст обращение модели. При отсутствии локальной копии нужные веса будут скачаны, поэтому первый запуск может занять заметно больше времени, чем последующие:

```bash
.venv/bin/python -m examples.01_refund --model multilingual \
  --text 'За март списали оплату дважды. Прошу вернуть повторное списание.'
```

Параметр `--text` содержит текст обращения. Через `--model multilingual` мы явно выбираем многоязычный вариант Laya, который подходит для работы с русским текстом. Без `--device` библиотека выбирает доступное устройство сама. Если нужно указать его прямо, добавьте `--device cpu` или `--device cuda`; второй вариант имеет смысл только при доступном CUDA backend, то есть подходящей вычислительной поддержке в установленном PyTorch.

После выполнения программа напечатает **JSON**. Это текстовый формат, где данные записаны как именованные поля: например, `"action": "review"`. Его удобно читать человеку и передавать другой программе. В выводе нашего примера есть три основных части: `runtime` с версиями и настройками, `result` с полным ответом Laya и `decision` с решением прикладного кода.

Чтобы не потеряться в большом ответе, сначала можно смотреть на несколько полей:

- `result.routing.model` показывает, какие веса действительно выбраны;
- `result.answers` содержит ответы на заданные вопросы; каждый ответ находится под именем своего вопроса;
- `result.usage.truncated` сообщает, пришлось ли отрезать часть текста из-за ограничения длины;
- `decision.action` и `decision.reason` объясняют, что рекомендует программа и по какой причине.

Внутри `answers` вопрос о возврате называется `refund_requested`. Его поле `noul` содержит оценку вероятности ответа «да». Это ещё не готовое распоряжение вернуть деньги: рядом с моделью работает отдельная *политика решения*, то есть обычные правила на Python, которые определяют, когда ответ можно использовать, а когда нужна ручная проверка.

Поэтому **по умолчанию `decision.action` будет `review`** — «передать на проверку». Такое поведение не означает, что модель не загрузилась. Оно означает, что выбранные пороги пока не признаны надёжными на ваших данных. Флаг `--validated-policy` разрешает политике выдавать другие рекомендации, однако сам по себе он ничего не проверяет и не обучает. Использовать его стоит после проверки качества, а не только ради того, чтобы исчезло слово `review`.

Здесь остаётся важное различие. Даже если модель правильно заметила просьбу о возврате, она не проверила факт оплаты, права клиента и предыдущие возвраты. Эти сведения должны проверяться отдельно. Ни один из примеров не выполняет денежную операцию.

## 4. Шесть сценариев

Все примеры устроены вокруг одной идеи, но решают разные задачи. Сначала мы формулируем вопрос и допустимые ответы. Затем Laya возвращает свои оценки, после чего Python-код решает, достаточно ли оснований для рекомендации. Поэтому, разобравшись с первым примером, вы уже будете узнавать знакомые части в остальных.

| Модуль | Для чего нужен | Какой ответ используется |
|---|---|---|
| [examples.01_refund](examples/01_refund.py) | Найти явную просьбу вернуть деньги | `noul`: вероятность «да», два порога и возможность отказаться от решения; дополнительно можно применить калибровку |
| [examples.02_route](examples/02_route.py) | Предложить отдел для обработки обращения | `choice`: выбор одной категории и вероятности всех вариантов |
| [examples.03_moderation](examples/03_moderation.py) | Проверить несколько отдельных признаков риска | Несколько вопросов `noul`; результат служит рекомендацией, а не гарантией безопасности |
| [examples.04_priority](examples/04_priority.py) | Оценить срочность по описанному влиянию проблемы | `score`: средний ожидаемый уровень и отдельно самый вероятный уровень |
| [examples.05_batch](examples/05_batch.py) | Обработать файл обращений и не потерять соответствие ответов исходным записям | Чтение ограниченными порциями, совместные вычисления и явная отметка завершения |
| [examples.06_api](examples/06_api.py) | Вызывать четыре политики из другого приложения по HTTP | Сервер FastAPI с ключом доступа и ограничением одновременных вычислений |

Имена `choice`, `score` и `noul` принадлежат API Laya. API здесь означает набор доступных программе команд и форматов данных. Вместо запоминания названий полезнее держать в голове различие: выбрать одну категорию, оценить уровень по шкале или ответить на вопрос «да/нет» через вероятность.

Примеры нужно запускать через `python -m`: так Python находит не только выбранный файл, но и общий пакет `production/`. Если скопировать один скрипт в случайную папку, не перенеся остальной код, его импорты работать не будут.

```bash
.venv/bin/python -m examples.02_route --model multilingual --text 'Не получается войти в приложение.'
.venv/bin/python -m examples.03_moderation --model multilingual --text 'Не согласен с ценой, но спасибо за помощь.'
.venv/bin/python -m examples.04_priority --model english --text 'Production checkout is unavailable for all customers.'
```

Параметры каждого сценария доступны через `--help`. Общие параметры сохраняются: `--model` выбирает модель, `--device` — устройство, `--max-len` — общий предел длины входа в токенах, `--head-max-len` — бюджет части с вопросом и вариантами, `--batch-size` — размер группы состояний для совместного вычисления, а `--max-loaded` — сколько моделей Router может держать загруженными. Токен — это часть текста после разбиения специальной программой, поэтому число токенов не обязано совпадать с числом слов или символов.

Полные объяснения этих ограничений находятся в руководствах. Здесь важно прежде всего не увеличивать значения наугад: более длинный контекст или больший пакет могут потребовать больше памяти, а более подробный вопрос оставляет меньше места для самого обращения.

### Выбор checkpoint

В документации часто встречается слово **checkpoint**. Так называют сохранённое состояние обученной модели: её веса вместе с конфигурацией и необходимыми файлами. В нашем случае можно выбрать один из трёх официальных вариантов, а можно поручить выбор Router. Router — это часть библиотеки, которая решает, какие веса использовать для данного запроса.

| `--model` | Когда его выбирать |
|---|---|
| `english` | Для английского текста: `convaiinnovations/laya` |
| `multilingual` | Для русского и других поддерживаемых языков: `convaiinnovations/laya-multilingual` |
| `typed-decisions` | Для англоязычных специализированных последовательностей решений: `convaiinnovations/laya-typed-decisions` |
| `auto` | Чтобы Router выбрал вариант по языку; все три модели при этом не голосуют за общий ответ |

Точные версии опубликованных файлов, то есть **Hub revisions**, записаны в [models.lock.json](models.lock.json). Это позволяет не зависеть молча от того, обновил ли автор модель на Hugging Face.

При этом одинаковые методы Python не делают все веса одинаково подходящими для любой задачи. Англоязычный вариант нельзя считать проверенным для русского, а специализированный `typed-decisions` не начинает лучше решать произвольный вопрос только из-за своего названия. Автоматическое распознавание его специальных последовательностей вопросов в нашей обвязке выключено, поэтому его нужно выбирать явно. Расширение `--max-len 8192` предназначено прежде всего для multilingual; его пользу и расход памяти тоже нужно проверять на своих текстах.

## 5. Пакетная обработка

Один запрос удобно изучать отдельно. Однако в реальной работе часто уже есть файл с сотнями или тысячами обращений. Для такого случая предназначен пятый пример: он читает записи небольшими порциями и передаёт несколько состояний в совместное вычисление, вместо того чтобы загружать отдельную модель для каждой строки.

```bash
mkdir -p outputs
.venv/bin/python -m examples.05_batch \
  --model multilingual --schema route \
  --input data/tickets.jsonl --output outputs/tickets-route-001.jsonl \
  --chunk-size 32 --batch-size 8
```

`mkdir -p outputs` создаёт папку для результатов. В `--input` указан учебный файл, а `--output` задаёт новое имя выходного файла. Параметр `--schema route` означает, что для всех записей мы задаём вопросы о маршрутизации. Вместо `route` доступны `refund`, `moderation` и `priority`.

Вход записан в формате **JSONL**: каждая строка содержит отдельный JSON-объект, например `{"id":"ticket-001","text":"Текст обращения"}`. Поле `id` помогает потом понять, какому обращению принадлежит ответ. Готовый файл [data/tickets.jsonl](data/tickets.jsonl) содержит вымышленные русские и английские обращения, а не настоящие данные клиентов.

Здесь легко спутать два похожих параметра. `--chunk-size 32` задаёт, сколько записей приложение читает в очередную порцию, а `--batch-size 8` ограничивает число состояний в одной группе вычислений модели. Это разные уровни работы. Файл может быть большим, хотя в конкретный момент программа обрабатывает только его часть. При этом для обнаружения повторных ID она всё равно хранит их множество, поэтому общий расход памяти не строго постоянный.

Выходной файл должен быть **новым**. Программа специально отказывается перезаписывать существующий, чтобы случайный повтор команды не уничтожил предыдущий результат. Успешную обработку подтверждают одновременно код завершения 0 и последняя запись `run_end` со `status=complete`. Если программа оборвалась, часть ответов уже могла сохраниться, однако такой файл считается незавершённым — partial. Для нового запуска выберите другое имя. Подробный формат и ограничения описаны в [разделе batch](02_PRODUCTION.md#9-пример-05-пакетный-jsonl).

## 6. HTTP API

До этого мы вызывали Laya из терминала. Но другой программе может быть удобнее отправлять текст на уже работающий сервер и получать JSON в ответ. **HTTP API** как раз предоставляет такой способ общения: клиент посылает запрос на определённый адрес, а сервер проверяет его, вызывает модель и возвращает результат. Серверный код в этом проекте написан на FastAPI, библиотеке для Python.

Сначала нужно задать собственный ключ доступа. Он хранится в **переменной окружения** `LAYA_API_KEY`: это настройка процесса, которую программа читает при запуске. Ключ не нужно записывать в исходный код или публиковать в Git.

**Bash/Zsh:**

```bash
export LAYA_API_KEY="$(.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))')"
```

**Fish:**

```fish
set -gx LAYA_API_KEY (.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))')
```

Обе команды делают одно и то же: создают случайный секрет и передают его будущему серверному процессу. Отличается только синтаксис оболочки. После этого сервер можно запустить:

```bash
.venv/bin/python -m examples.06_api --model multilingual --host 127.0.0.1 --port 8000
```

Адрес `127.0.0.1` означает, что к серверу обращаются с того же компьютера, а `8000` — номер порта, по которому его можно найти. Порт — не имя модели и не дополнительная GPU: это часть сетевого адреса программы. Для явного выбора GPU можно добавить `--device cuda`.

При запуске сервер заранее загружает веса. Это называется **preload** и переносит время загрузки с первого клиентского запроса на запуск приложения. Если выбрать `--model auto`, наш API заранее загрузит все три варианта и потребует больше памяти, чем один multilingual. При этом факт успешной загрузки говорит только о готовности выполнить вычисление, а не о проверенной точности ответов.

В другом терминале нужно задать **то же значение** `LAYA_API_KEY`, а не сгенерировать новое. Иначе сервер и клиент будут использовать разные секреты. Затем можно проверить готовность и отправить пример обращения:

```bash
curl --fail-with-body http://127.0.0.1:8000/readyz
curl --fail-with-body http://127.0.0.1:8000/v1/decide \
  -H "X-API-Key: $LAYA_API_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @data/api_request.json
```

`curl` — программа для отправки HTTP-запросов. В первой команде она обращается к `/readyz`, чтобы узнать, закончил ли сервер подготовку моделей. Во второй — передаёт содержимое файла как тело запроса на `/v1/decide`. Через `-H` задаются заголовки: ключ доступа и указание, что данные записаны в JSON.

В теле запроса нужны `text` с обращением и `scenario` с названием задачи: `refund`, `route`, `moderation` или `priority`. Необязательное поле `request_id` помогает сопоставлять запрос и ответ. Адрес `/healthz` сообщает, что обработчик жив, а `/readyz` — что закончилась подготовка. Это два разных вопроса: процесс может существовать, но ещё не быть готовым к работе.

Ошибки тоже имеют свой смысл. Код 401 означает, что не подошёл ключ; 422 — что содержимое запроса не соответствует ожидаемому формату. Наш сервер выполняет только одно предсказание одновременно, поэтому занятый вычислительный слот приводит к 429, а недоступный инференс — к 503. *Инференсом* здесь называется применение уже обученной модели к новому тексту, в отличие от обучения её весов.

Без отдельно проверенных политик ответы остаются `review`, как и в CLI-примерах. Для публичного сервиса одного статического ключа недостаточно: понадобятся шифрование соединения TLS, ограничения размера и частоты запросов, а также подходящая система доступа. Все эти границы и поведение сервера разобраны в [разделе API](02_PRODUCTION.md#10-пример-06-http-api).

## 7. Docker

При переносе программы на другой компьютер часто обнаруживается, что версии библиотек отличаются. Docker помогает упаковать приложение и его программное окружение в **образ**. Из этого образа запускается **контейнер** — отдельный работающий экземпляр программы. Это не отменяет зависимость от оборудования и драйверов, но делает состав программного окружения более явным.

В проекте уже есть Dockerfile с описанием сборки и файлы Compose с настройками запуска. Compose позволяет не перечислять каждый параметр контейнера вручную. Перед запуском задайте `LAYA_API_KEY` способом для своей оболочки из предыдущего раздела.

**CPU:**

```bash
docker compose up --build
```

**NVIDIA GPU:**

```bash
docker compose -f compose.yaml -f compose.gpu.yaml up --build
```

Параметр `--build` просит сначала собрать образ, а затем запустить сервис. Во втором случае настройки из `compose.gpu.yaml` дополняют основной файл: выбирают CUDA-сборку и доступ к GPU. Для этого нужны совместимый драйвер, NVIDIA Container Toolkit — поддержка NVIDIA GPU в контейнерах — и версия Compose, которая понимает `gpus: all`.

При первом запуске веса сохраняются в отдельный **volume**, то есть хранилище Docker для файлов, которые должны пережить пересоздание контейнера. В данном случае это кеш моделей: их не нужно повторно скачивать только потому, что был заменён контейнер. Сетевой порт опубликован лишь на `127.0.0.1:8000`, а приложение работает не от имени root, то есть не получает автоматически права системного администратора внутри контейнера.

Здесь приведён способ запуска, а не результат выполненной Docker/GPU-проверки. Офлайн-контейнеры, права на файлы и запуск обычных CLI внутри образа подробно разобраны в [разделе Docker](02_PRODUCTION.md#12-docker-cpu-и-nvidia-gpu).

## 8. Офлайн, калибровка и адаптация

После первых примеров обычно появляются три вопроса: можно ли работать без интернета, как задать свою задачу и насколько можно доверять числам модели. Они связаны с разными частями системы, поэтому лучше разбирать их отдельно.

**Работа без интернета** требует заранее подготовленных файлов. На машине с разрешённым доступом к Hugging Face выполните `.venv/bin/python -m tools.download_models --model all --directory models`. Эта команда скачает выбранные версии трёх моделей. Затем нужно перенести их на целевую машину и задать локальные пути и запрет сетевых обращений по [инструкции](02_PRODUCTION.md#3-все-чекпоинты-hub-и-офлайн). Наличие программы или пустой папки кеша само по себе веса не заменяет.

**Своя задача** начинается не с изменения архитектуры, а с понятной формулировки вопроса и вариантов. Они находятся в [production/schemas.py](production/schemas.py). Например, в одном проекте просьба вернуть деньги и вопрос о статусе уже оформленного возврата считаются разными намерениями, а в другом их могут объединять. Это нужно решить до оценки качества. Изменение описаний и даже порядка вариантов способно поменять ответ, поэтому старые измерения и калибровку после такой правки нельзя автоматически считать действующими.

**Калибровка** нужна, когда мы хотим проверить, насколько численные оценки согласуются с наблюдаемыми результатами. Если модель часто ставит очень высокую вероятность ошибочным ответам, одного высокого порога недостаточно. В нашем примере дополнительная температура меняет резкость распределения, однако не учит модель отличать правильный класс от неправильного и не исправляет перепутанные ответы «да» и «нет».

Полный процесс `tools.calibrate collect → fit → evaluate` и применение калибровки в первом примере приведены в [отдельном разделе](02_PRODUCTION.md#11-калибровка-без-выдуманного-logits-api). На этапе `collect` выполняется модель и собираются её ответы, на `fit` подбирается параметр, а на `evaluate` результат проверяется на другой выборке. Учебные файлы показывают только этот порядок действий: их недостаточно, чтобы подтвердить надёжность реального сервиса. Кроме того, наш файл калибровки имеет собственный формат и не передаётся в официальный `agent.load_calibration`.

И наконец, важно смотреть не только на красивую вероятность. Само поле `confidence` не является гарантией правильности, а отрезанный при подготовке текст может лишить модель нужных фактов. Поэтому решение о запуске принимают по проверке на своих размеченных данных, цене ошибок и допустимому объёму ручной работы, а не по одному удачному письму.

## 9. Проверки без запуска моделей

Часть поведения можно проверить без нейросети. Например, можно убедиться, что политика не разрешает автоматическое действие без подтверждения, что повреждённое число приводит к ручной проверке, а калибровочные данные не пересекаются с проверочными. Такие проверки касаются нашего Python-кода, а не способности Laya понимать текст.

Для них достаточно стандартной библиотеки Python; скачивать веса и устанавливать полный ML-стек не нужно:

```bash
python3 -B -m unittest discover -s tests -v
```

При подготовке прошли 18 таких тестов. Также проверялись справка команд, HTTP-ответы до обращения к модели, численный пример работы калибровки и выбор модели настоящим Router без загрузки весов. Эти результаты не нужно путать с проверкой качества инференса, скорости GPU или сборки Docker. Что именно выполнялось, а что нет, записано в [delivery_manifest.json](delivery_manifest.json). Для проверки на своей машине предусмотрен [чек-лист](02_PRODUCTION.md#13-приёмка-на-своей-машине).

## Что хранить в Git

В репозиторий входят документы, исходный код, вымышленные примеры в `data/`, зависимости и Docker-файлы. Это то, чем можно поделиться, чтобы другой человек понял проект и повторил запуск в своём окружении. Настоящие обращения пользователей, ключи доступа и файлы весов к этой категории не относятся.

Файл `.gitignore` уже исключает `.venv/`, `.env`, `models/`, `outputs/` и Python-кеш. Однако он не распознаёт секрет по смыслу, если тот случайно оказался в обычном скрипте или документе. Поэтому перед коммитом всё равно нужно смотреть, какие данные отправляются на GitHub. `.env.example` служит только образцом настроек; действующие API/Hugging Face токены в нём хранить не следует.

Прикладные политики этого проекта не переводят деньги, не удаляют сообщения и не отправляют обращения во внешние сервисы. Если позднее вы подключите такое действие, его безопасность должна обеспечиваться отдельными правами, бизнес-проверками, журналом операций и защитой от повторного выполнения. Последнюю часто называют *идемпотентностью*: повтор одного запроса не должен случайно вызвать второй возврат денег. Именно с учётом этих границ и стоит воспринимать репозиторий — как подробный материал и работающие примеры для дальнейшей проверки, а не как заранее выданное разрешение доверить модели любое решение.
